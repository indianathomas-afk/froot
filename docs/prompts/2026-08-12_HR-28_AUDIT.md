## 1. The problem, as observed in code

`TrainingModule.description` was authored through a plain `<textarea>` ([training-form.tsx:826](../../src/app/(app)/hr/training/training-form.tsx), pre-change) and rendered through a bare `<p>` ([training-module-view.tsx:100-101](../../src/components/hr/training-module-view.tsx), pre-change):

```tsx
{description && (
  <p className="text-sm text-[var(--color-muted-foreground)] mt-1">{description}</p>
)}
```

No `whitespace-pre-wrap`. So an admin who typed a description with paragraph breaks and a bullet-ish list saw every newline collapse into a single run-on line on the trainee's screen. The authoring tool accepted structure the renderer discarded.

Note that the LESSON body next to it does not have this bug — `lesson.info` already renders with `whitespace-pre-wrap` (`training-module-view.tsx:155`). So the description was the odd one out, and the fix direction was already half-established in the same file.

## 4. Export round-trip — examined, deliberately left alone

`csv.ts:54` emits `description` verbatim into the export cell, so after HR-28 an exported module carries `<p>…</p>` in that column.

Considered stripping to plain text on export. **Rejected:** it would destroy formatting on re-import, and export→import is the path an operator uses to bulk-edit modules. HTML now round-trips faithfully, and with §3's fix the return leg is sanitized. The only cost is that a human reading the raw CSV sees tags — acceptable, and preferable to silently downgrading their content.

## 5. The predicate — a real bug, found by testing, not by reading

The HTML/plain-text distinction is load-bearing in three places: the editor (convert or not), the sanitizer (sanitize or pass through), the renderer (`dangerouslySetInnerHTML` or text node). It started as a full tag-shaped match:

```
/<\/?[a-z][a-z0-9-]*(\s[^>]*)?\/?>/i
```

A local harness over sixteen inputs found this classifies **`<svg/onload=alert(1)>` as plain text** — the `/` is followed by a letter, not `>`, so the regex does not match. That input was therefore **stored without sanitizing**.

Measured impact: **no XSS**. The renderer branches on the same predicate, so it took the plain-text branch and emitted a React text node, which escapes the string. The user sees the literal characters.

Measured *risk*: the safety was resting on this regex agreeing with every present and future caller, rather than on the stored string being harmless. That is the wrong thing to depend on — one future component that innerHTMLs a description without the branch turns a storage quirk into a vulnerability.

**Fixed by copying the HTML tokenizer's own rule** — a browser starts a tag at `<` followed by an ASCII letter, or `</`; everything else is text:

```
/<\/?[a-z]/i
```

Now "stored as plain text" means "no browser can find a tag in here", which is the property the text-node branch is entitled to assume.

**The cost, named:** a legacy description containing something like `the <name> field` now takes the sanitizer branch and loses that literal, because DOMPurify drops the unknown tag and keeps its content. This is the correct side to err on — a browser handed the same string reads it as a tag too — but it is a behavior change on existing rows and is recorded rather than buried.

## 6. Why plain text bypasses the sanitizer rather than passing through it

Non-obvious, and it is a **correctness** requirement, not an optimisation.

DOMPurify entity-encodes bare ampersands. Run a CSV-imported `Tom & Jerry` through it and the column stores `Tom &amp; Jerry`. The renderer then still finds no tag, takes the plain-text branch, and emits a text node — showing staff the literal string `Tom &amp; Jerry`.

So `sanitizeRichText` returns tag-free input verbatim. This is not a hole: text with no tag in it cannot carry a script, and §5's predicate is now as permissive as the parser, so anything a browser would read as markup — including `<script>` and `<svg/onload=` — takes the sanitizer branch.

## 7. Toolbar/allowlist coupling

Tiptap's StarterKit v3 ships **heading, link, code, codeBlock, blockquote, strike, underline** enabled by default. The allowlist is `p br strong em b i ul ol li`.

Left at defaults, `Cmd-Alt-1` makes a heading, the admin saves, and the server strips it — formatting that appears to work and then silently doesn't, which is worse than formatting never offered. All seven are disabled at the source in `EXTENSIONS`.

`trailingNode` is also disabled, for a different reason: it inserts a real empty paragraph so there is always somewhere to click below the last block, and it **serialises** — a description ending in a list would be stored as `<ul>…</ul><p></p>` and render with a stray gap.

Rule recorded in both files: adding a toolbar button means adding its tag to the allowlist, in the same commit.

## 8. Three files, not two

The prompt specified two new files. Shipped three, approved in advance.

`sanitize-html.ts` imports `isomorphic-dompurify`, which pulls in **jsdom**. The editor is a client component and needs the same HTML/plain-text predicate. Importing the sanitizer from the browser to reach one regex risks dragging jsdom into the client bundle — an ESM static import of a side-effectful package is not reliably tree-shaken.

The alternative was defining the predicate twice, which this codebase pointedly avoids (cf. HR-25's `SELF_FILES_SERVED_WHERE` / `selfFilesServed()` — "two expressions of one rule kept adjacent so they cannot drift"). Here they would not even have been adjacent.

So `src/lib/rich-text.ts` holds the pure half — `looksLikeHtml`, `isEmptyRichText`, `plainTextToHtml` — with no dependencies at all, imported by both sides.

---

## 9. Empty-state normalisation

Tiptap serialises an emptied editor as `<p></p>`, a truthy string. Without handling, an admin who clears the description leaves a blank paragraph rendering forever and a column holding markup that means nothing.

Handled in two places, deliberately:
- **Editor** emits `""` rather than `<p></p>` (`editor.isEmpty`), so the payload says what the admin did.
- **Server** normalises to `null` via `isEmptyRichText`, which tests TEXT — tags stripped, `&nbsp;` counted as whitespace — so `<p><br></p>` and `<ul><li></li></ul>` are both empty, while `&amp;` is not.

The server half is the one that matters; the client half is courtesy. A client is never the gate.

### 10.2 Editor + renderer, in a browser

Dev server, temporary page under the public `/menu` route (public per `proxy.ts:11`), **deleted before the commit**.

- Editor box matches Input/Textarea — same border token, radius, shadow; focus ring moved to `focus-within` because the focusable element is the contenteditable inside.
- Bold with a live selection works — `onMouseDown` preventDefault holds the selection through the button press. `aria-pressed` tracks active state, so `useEditorState` reactivity is wired correctly.
- Bullet and numbered lists produce `disc` / `decimal` markers at `padding-left: 20px` **inside the editor**, i.e. Tailwind preflight is defeated on both sides.
- Legacy plain text loads as `<p>line<br>line</p><p>para</p>` — readable, breaks intact — and **does not fire `onChange`**, so opening an old module and not touching the description does not dirty it.
- Typing after a legacy load emits HTML, converting the row on save. No cursor-reset loop from the sync effect.
- Clear emits `""` and the placeholder returns.
- Hostile input renders as `<p>safe</p>` — script and img absent from the DOM.
- **No console errors**, so `immediatelyRender: false` handled SSR hydration.

**One defect found and fixed here:** Tiptap wraps list-item content in `<p>`, so real editor output is `<li><p>text</p></li>`. The renderer's `[&_p]:mb-2` applied inside every bullet and spaced the list out like body copy. `[&_li_p]:mb-0` added to **both** the editor content class and the renderer, kept identical so the builder is a true preview.
