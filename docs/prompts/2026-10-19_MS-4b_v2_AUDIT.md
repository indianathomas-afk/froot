### The seams MS-4b touches, named exactly

1. **`define.ts`** — `batch` becomes a discriminated union. A
   `"per-intent"` kind keeps `render(payload, org, to)`. A
   `"per-recipient-daily"` kind supplies `renderGroup(items, org, to)` instead,
   where `items` is every intent queued for that recipient in this dispatch.
   Optional `sample(org)` returns a sample payload list. The three existing kind
   files do not change.
2. **`define.ts` `NotificationOrg`** — gains `milestoneAlertsEnabled`, and
   **also `clerkOrgId`, `activeModules`, `milestonesEnabled` and the checklist
   switch**. Without them the kind's `enabled` cannot apply
   `milestonesActive()`. The prompt names only the first. `ORG_SELECT` in
   `dispatch.ts:271` grows to match, and the checklist switch is read through
   the `milestoneSettings` relation in the same query.
3. **`enabled(org, intent)`** — gains the intent as a second argument, so a
   checklist intent can expire when F13 is turned off while a tenure intent in
   the same org still sends. The existing kinds ignore the second argument.
4. **`exclude` becomes awaitable** (`boolean | Promise<boolean>`). No kind uses
   it today. The milestone kind must compare against the StaffMember's
   CURRENT `userId` and `email`, so it reads them at dispatch. Today's
   signature is sync and gets only (intent, recipient).
5. **`dispatchNotifications`** — after loading intents, it splits them by
   their kind's `batch`. Per-intent intents go through `dispatchOne`
   **unchanged**. Grouped intents go to a new `dispatchGrouped(intents,
   transport, trigger, now)`, one call per (org, kind).
6. **`dispatchGrouped`** (new, in `dispatch.ts`) does freshness and org switch
   per intent, exactly as `dispatchOne` does. Then for each intent it runs
   `eligibleRecipients` and the P6 filter. It builds a map of
   **recipient → [intents that recipient is eligible for and has no `sent`
   delivery on]**, and for each recipient:
   - **live**: `claim()` every (intent, recipient) pair. Pairs that cannot be
     claimed drop out of this email. Render ONE email from the claimed
     intents, send it once, write ONE `NotificationMessage`, and point every
     claimed `NotificationDelivery.messageId` at it, settled `sent`/`failed`.
     Then `finalize()` each touched intent by its own delivery rows, exactly as
     today. **P6 holds per (milestone, recipient)**: a failed summary leaves
     those pairs `failed`, and the retry sends a summary of only those pairs.
   - **sandbox**: one email to an allow-listed recipient, no delivery rows, no
     state change (R1). Skipped entirely on `trigger: "sweep"` (R2).
   - **dry-run**: one dry-run message per recipient, covering only the intents
     not already dry-run-logged to that recipient. **This is the seam that
     needs a schema change** (below).
7. **`writeMessage`** — takes the list of intents a message covers. For a
   per-intent kind the list has one element and the row is byte-identical to
   today's.
8. **`recordUndispatchable`** — calls `renderGroup([payload])` for a grouped
   kind.
9. **The `known` write** — a new export `recordKnownNotification(args)` in
   `dispatch.ts`. It **creates a row in state `known` only when no row exists
   for the key**. Any existing row, in any state, is left alone. A
   unique-violation race is also a no-op. `enqueueNotification` is not
   changed.
10. **`/api/notify/test`** — accepts `?kind=milestone.reached` (query string,
    still no body). The only accepted values are kinds that define `sample()`.
    It still enqueues a **`test`** intent, with the recipient still the caller's

    delegates to the sampled kind's `renderGroup(sample(org))` with the subject

11. **`listRecentEmails`** — **the reader still needs the label.** It reads
    `KIND_LABELS`, not the registry. Lean: switch both reads (`:261`, `:379`)
    to the registry's `kindLabel()`, so a new kind is labelled by its own

### Does either change need a schema change?

**The `known` write: no.** `state` is TEXT and `known` is already a valid
value.

**The grouping mode: YES, one additive column. This is new fork N1.** The
live path needs nothing: `NotificationDelivery(intentId, recipient)` already
links each pair to its `messageId` (confirmed: `@@unique([intentId,
recipient])`, `messageId String?`), and `NotificationMessage.intentId` is
nullable. The prompt's schema note is right **for live**.

It is not right for **dry-run**. Delivery rows are live-only by design (R1;
`schema.prisma:941`), so a dry-run summary has nowhere to record which
milestones it covered. `NotificationMessage.intentId` holds one intent, not
several. Today's "log a dry run once per (intent, recipient)" rule
(`dispatch.ts:395-403`) cannot be kept for a summary without that link. Each
daily run would re-list every queued milestone for up to 7 days. Production
runs in dry-run by default (ruling 5), so that is a week of duplicate rows per
recipient.

Options:

- **(a) `NotificationMessage.intentIds String[] @default([])` — LEAN.** One
  additive column, the `hrAckRecipients String[]` precedent. A grouped message
  stores every intent it covered. `intentId` stays null on a summary, and a
  per-intent message keeps `intentId` and leaves `intentIds` empty, so the three
  existing kinds write byte-identical rows. Dry-run dedupe for a grouped kind
  becomes `{ kind, mode: "dry-run", to, intentIds: { hasSome: [...] } }`. No FK
  is needed: intents are kept forever (P5), and a pruned message only means a
  dry run could log again after 180 days.
- (b) A join table `NotificationMessageIntent(messageId, intentId)`. It has
  referential integrity, but it is a new model and a second write per covered
  intent. It only buys anything if a reader needs to walk message → intents,
  and none does yet.
- (c) No schema: dedupe dry-run by "intent created after this recipient's last
  dry-run summary". That is a heuristic. It silently drops a milestone for a
  manager assigned to the store after the intent was created.
- (d) No dedupe: a dry-run summary every day. That is honest, but noisy.

So the migration is `Organization.milestoneAlertsEnabled Boolean
@default(false)` **plus** `NotificationMessage.intentIds TEXT[] NOT NULL
DEFAULT ARRAY[]::TEXT[]`, if Gary takes N1(a).

## B2. What production does on deploy (ruling 5: provider unset)

**Nothing at all, and that comes before the mode table applies.** Production
has `milestoneAlertsEnabled` = false on every org (the new column's default).
The producer leg queries only orgs with the switch on AND `milestonesActive()`,
so it enqueues nothing and dispatches nothing. MS-1…MS-4a are `status:
staging` (`docs/ROADMAP.yaml`), and production also has no milestone rows of
its own until they promote.

**Once an org's switch is on, production is a dry run that consumes nothing.
Checked at source, not inferred:**

1. `deliveryMode()` (`notify.ts`) → unset → `"console"` → `"dry-run"`.
2. A dry-run dispatch never reaches `finalize`: `dispatchOne` returns at
   `dispatch.ts:474-477` when `transport.mode !== "live"`. `dispatchGrouped`
   will have the same structural early return, and the fixture asserts it.
   **The intent stays `queued`. No delivery row is written** (`claim()` is only
   reached on the live branch, `:458`).
3. Nothing writes `known` to an existing row. The producer's `known` write
   is create-only (seam 9), and `enqueueNotification` never writes it. So a
   dry-run intent cannot be turned into `known` by a later producer run.
4. It leaves `queued` only by **freshness**. `dispatchOne`/`dispatchGrouped`
   expire a `queued` intent once `now − eventAt` exceeds the kind's window.
   The hourly sweep does this too (freshness runs before mode, `:357`). So it
   ends `expired`, never `sent` or `known`.
5. **Switching Resend on later**: the next producer run (15:00 UTC) re-enqueues
   every milestone reached within 7 days. Those intents are still `queued`, so
   `enqueue` refreshes them (same `eventAt`, the reach date), and the live
   dispatch sends them. A milestone more than 7 days old is either `expired`
   (the producer's `known` write is a no-op on it) or absent (the producer
   writes `known`). **Neither is ever sent.**

**One correction to the prompt, needed for (4)/(5) to hold at the boundary
— new fork N2.** The prompt says "Freshness for the kind is 7 days (10080
minutes)". Ruling 2 dates a milestone on the day it was reached, so
`eventAt` = the store-local **midnight** of the reach date
(`localMidnightUtc(reachedOn, zone)`). The cron runs at 15:00 UTC = 08:00 PDT.
A milestone reached on day D that is exactly 7 days old on D+7 is "not more
than 7 days" and should send. But at 08:00 on D+7, `now − eventAt` = 7 days 8
hours > 10080 minutes, so **the dispatcher would expire it in the same run
that enqueued it**. The producer's day count and the dispatcher's minute count
disagree for one day in eight. Lean: **freshness 8 days (11520 min)**. The
producer is the 7-day judge, and freshness is the backstop. A milestone
reached on D can then be sent through local day D+7 and never on D+8: any
moment of local D+8 is ≥ 8 days past midnight D. The alternative, keeping 10080
and having the producer send only ≤ 6 days, changes ruling 2's "more than 7
days".

**Q-B3b — A4 extended with the checklist half. What a first run would send
vs record `known`:**

```sql
WITH org AS (SELECT 'cmr54z65v000105jxczpt72w1'::text AS id),
tenure AS (
  SELECT sm.id AS staff_id, 'tenure'::text AS kind, tm.id AS milestone_id,
         (sm."startDate" + tm."dayCount")::date AS reached_on
  FROM "StaffMember" sm
  JOIN "TenureMilestone" tm ON tm."organizationId" = sm."organizationId"
  WHERE sm."organizationId" = (SELECT id FROM org)
    AND sm.status = 'ACTIVE' AND sm."startDate" IS NOT NULL
    AND NOT tm."isArchived"
    AND sm."startDate" + tm."dayCount" <= CURRENT_DATE
),
named AS (
  SELECT sm.id AS staff_id, tl."completedAt",
         row_number() OVER (PARTITION BY sm.id ORDER BY tl."completedAt", tl.id) AS n
  FROM "TaskLog" tl
  JOIN "Checklist" ch ON ch.id = tl."checklistId"
  JOIN "StaffMember" sm ON sm.id = tl."completedByStaffId"
                       AND sm."organizationId" = ch."organizationId"
  WHERE sm."organizationId" = (SELECT id FROM org) AND sm.status = 'ACTIVE'
),
checklist AS (
  SELECT n.staff_id, 'checklist'::text AS kind, cm.id AS milestone_id,
         n."completedAt"::date AS reached_on
  FROM named n
  JOIN "ChecklistMilestone" cm ON cm."organizationId" = (SELECT id FROM org)
                              AND cm."taskCount" = n.n
                              AND NOT cm."isArchived"
),
allm AS (SELECT * FROM tenure UNION ALL SELECT * FROM checklist)
SELECT current_setting('neon.branch_id', true) AS branch,
       a.kind,
       count(*)                                                        AS reached_total,
       count(*) FILTER (WHERE a.reached_on >= CURRENT_DATE - 7)        AS would_send,
       count(*) FILTER (WHERE a.reached_on <  CURRENT_DATE - 7)        AS would_be_known,
       count(DISTINCT a.staff_id) FILTER (WHERE a.reached_on >= CURRENT_DATE - 7) AS people_in_window
FROM allm a
GROUP BY 1, 2
ORDER BY 2;
```

## B5. Could a send reach the employee or an out-of-scope manager?

Nothing does today, because no milestone send path exists. In the design:

1. **The employee, linked account** — `exclude` drops `user.id ===
   StaffMember.userId`, read at dispatch. Covered.
2. **The employee, unlinked account** — `exclude` drops a recipient whose
   address equals `StaffMember.email`, trimmed and case-insensitive (ruling
   4). **Residual, named:** an unlinked ADMIN/MANAGER whose `StaffMember.email`
   is NULL or differs from their `User.email` is still emailed about their own
   milestone. Nothing in the data ties the two records together, and ruling 4
   names exactly these two tests. COMMENT, not a fork.
3. **A manager about themselves** — the same `exclude`. The subject is the
   staff member, so it covers ADMINs too.
4. **An out-of-scope manager** — the resolver's MANAGER arm is
   `storeAssignments: { some: { storeId: { in: <member's StoreStaffAssignment
   storeIds> } } }`, read fresh. A member with no store assignment gets
   ADMINs only.
5. **Corporate** — `isCorporate` short-circuits to the ADMIN arm **before**
   the manager query is built. A corporate member synced with one assignment
   per store would otherwise pull in every manager.
6. **THE GROUPING MODE ITSELF — the new risk this phase creates.** A summary
   must list, for each recipient, only the intents **that recipient was
   eligible for**. The map is built per intent from that intent's own
   eligible list. It is never "every intent in the org to everyone eligible
   for any of them". If the grouping were built the second way, a Store A
   manager's summary would carry a Store B employee. **The fixture asserts it
   directly.**
7. **STORE / STAFF logins** — excluded by the role arm and by `can()`. The key
   is absent from `GRANTABLE_CAPABILITIES`, so it cannot be granted to them.
8. **The test send** — the `test` kind, caller-only, unchanged. `sample()`
   payloads are fixed fictional data, so no real employee is ever named in a
   test.
9. **Stale recipients** — resolved at every dispatch, never cached (F6).

## The plan

The prompt's Phase 2, steps 1–8, with these changes.

### New forks (need Gary)

**N1 — the dry-run link for a summary. Lean (a):
`NotificationMessage.intentIds String[] @default([])`.** This is the only
schema change beyond `milestoneAlertsEnabled`. See B1, "Does either change
need a schema change?". Without it, either production dry-run logs a summary
of every queued milestone every day for a week, or the dedupe is a heuristic
that drops milestones silently.

**N2 — freshness 8 days, not 7. Lean: 8 days (11520 minutes).** See B2. The
prompt's 10080 would expire a milestone reached exactly 7 days ago in the same
run that should send it. Ruling 2's "more than 7 days → known" stays exactly as
ruled; it is applied by the producer on store-local days.

### Implementation choices (for ratification)

- **C1 — kind id `milestone.reached`**, label "Milestone reached" (NOTIFY-3 §
  4.7's name). dedupeKey `${staffMemberId}:${tenure|checklist}:${milestoneId}`.
- **C2 — the producer dispatches only what it saw reached today.** After
  enqueueing, it dispatches with `intentIds` = this run's `queued` results
  (created or refreshed). It does not dispatch by `kinds` alone. A queued
  intent whose checklist count has since dropped (MS-4a: counts go down) is
  not re-announced. It ages out instead. A `sent` one is untouched either way
  (Gary's MS-4a ruling).
- **C3 — the sweep never makes a FIRST send of a grouped kind. It only
