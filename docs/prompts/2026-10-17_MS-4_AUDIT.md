the console logger. Any milestone email that fires on staging lands in a real

## A1. What "a checklist completed by an employee" means in the data

**Verdict: completions CANNOT be attributed to a person at the checklist level.
They can be attributed at the TASK level, only when someone picks a name, and
the picker makes naming optional.** Checklist milestones are possible only
with a definition Gary chooses (F0).

Evidence (paths relative to repo root):

- **`Checklist` has no "who" field.** `prisma/schema.prisma:713-722`: `storeId`,
  `status String @default("Pending")` (free text, not an enum), `completedAt`,
  `completionRate`. The submit route says it outright:
  `src/app/api/checklists/[id]/submit/route.ts:140` — "Checklist has no
  completedBy column of any kind — attribution lives on TaskLog rows".
- **`TaskLog` holds attribution, both fields nullable.**
  `prisma/schema.prisma:840-856`: `completedByUserId String?` (the logged-in
  Froot User), `completedByStaffId String?` (the StaffMember picked).
- **The task route** (`src/app/api/checklists/[id]/task-log/route.ts`):
  - `completedByUserId` = the session's user (`:92-94`, `:123`). On a shared
    store iPad that is the STORE device login (`src/lib/device-login.ts:10-13`),
    which says nothing about which person tapped.
  - `completedByStaffId` = whatever the client sends; the generic `"manager"`
    value is saved as null (`:103-104`, `:124`).
  - **Toggle semantics:** tapping a done task DELETES its log (`:97-100`).
    Un-tick and re-tick by someone else replaces the name. Only the latest
    ticker survives.
  - **DEFECT (F12-1):** the staff id is never checked against the org or the
    checklist's store. The FK only proves the StaffMember exists *somewhere*.
    Compare `src/app/api/calendar/occurrences/[id]/complete/route.ts:112-118`,
    which does check.
- **The picker** (`src/app/(app)/store-view/checklist/[id]/checklist-execution-client.tsx`):
  "Who completed this task?" opens whenever the store has staff (`:346-348`);
  buttons are "Team Member", "Manager" (both send `"manager"` → null) and one
  per StaffMember (`:584-608`). With no staff at the store, tasks save with no
  name (`:349-353`). It is the only caller of the task route.
  - **DEFECT (F12-2):** the picker's staff list
    (`src/app/(app)/store-view/checklist/[id]/page.tsx:47-54`) has no
    `status: "ACTIVE"` filter, so terminated staff are offered.
- **User ↔ StaffMember link:** `StaffMember.userId String? @unique`
  (`schema.prisma:450`). Most staff never get a login, so `completedByUserId`
  resolves to a person only for staff with their own linked login — not for
  shared devices.
- **Whole-checklist submit** writes status/completionRate/completedAt only
  (`submit/route.ts:92-130`); a checklist can leave "Completed" if a task is
  un-ticked and it is resubmitted (`:116-118`).
- **No per-person count exists today.** The only one is
  `prisma.taskLog.count({ where: { completedByStaffId } })` in
  `src/app/api/staff/[id]/route.ts:217`, used to block deletion.

**How often a name is actually picked** — measured on dev, which is a stale
fork of production:

```
dev br-broad-wave-a6vpjdw0  org cf888f2d-f234-48c7-8097-fd5b44b5b3dd
  TaskLog rows 38 · named staff 28 · unnamed 10 · distinct staff 3
  first 2026-06-28T20:26:26Z UTC · last 2026-07-24T01:01:08Z UTC
```

74% named, from three people, over a month of early use. That is too small and
too old to rely on. **Before F0 is ruled, Gary should run this on production in
the Neon console (read-only):**

```sql
SELECT current_setting('neon.branch_id', true) AS branch,
       count(*) AS logs,
       count(*) FILTER (WHERE tl."completedByStaffId" IS NOT NULL) AS named,
       count(DISTINCT tl."completedByStaffId") AS distinct_staff,
       min(tl."completedAt") AS first_utc, max(tl."completedAt") AS last_utc
FROM "TaskLog" tl
JOIN "Checklist" c ON c.id = tl."checklistId"
WHERE c."organizationId" = 'cf888f2d-f234-48c7-8097-fd5b44b5b3dd'
  AND tl."completedAt" > now() - interval '30 days';
```

If "named" is well under half, checklist milestones will under-count most
people and the third F0 option (park it) is the honest one.

**What the F0 lean means in code (MS-4a):** a person's count = distinct
`Checklist` rows with `status = 'Completed'` in their org having ≥1 `TaskLog`
with `completedByStaffId = person`. The date a checklist milestone is reached
= the `completedAt` of the Nth such checklist, in the store's time zone. The
count can go DOWN (un-tick + resubmit); the tab shows the live count, and the
sent-once record (MS-4b) means an email already sent is never re-sent or
recalled.

## A2. NOTIFY-2b template and NOTIFY-2c grid

**Adding an email type** touches four registries; there is no Prisma enum:

## A3. Sending, retries, de-dup, and staging

- **Triggers:** pace alert = cron `/api/cron/pace-alerts` (`"0 15 * * *"`,
  `vercel.json`), Bearer `CRON_SECRET` (`route.ts:17-23`). HR ack = an event
  (`hr-signed-pdf.ts:803` → `after()`). Test = POST `/api/notify/test`, which
  **no UI calls**.
- **De-dup:** pace alerts lock with `PaceAlertLog @@unique([storeId, month])`
  written BEFORE the send; P2002 = already alerted; on send failure the lock
  is deleted and the error rethrown (`pace-alerts.ts:164-182, 281-305`). No
  in-run retry. AuditLog has no unique constraint; no idempotency key goes to
  Resend. MS-4b copies the pace-alert shape: a sent-once row with a unique key,
  written before the send, removed if the send fails so tomorrow retries.
- **Production-only crons:** only because Vercel runs crons on production
  deployments (`docs/DEPLOY_LOG.md:80`, `:4411`). **No code checks
  `VERCEL_ENV`.** Anyone holding the staging `CRON_SECRET` can fire a cron on
  staging by hand.
- **Staging email: YES, REAL MAIL TO REAL ADDRESSES.** Code: unset/"console"
  logs only; "resend" sends, no fallback (`notify.ts:154-176`). Docs: staging
  runs `NOTIFY_EMAIL_PROVIDER=resend` (`schema.prisma:121`;
  `DEPLOY_LOG.md:1595` — "real manager addresses against fixture numbers, so
  leave the pace toggle OFF on staging"). Production was unset/"console" at
  the 2026-09-20 promotion (`DEPLOY_LOG.md:1164-1165`); switching it is listed
  as owed (`:1225-1226`) and **no later entry says it was switched** — Gary
  should confirm production's value in the Vercel dashboard (not by env pull).
- **No allowlist, redirect or test-recipient mechanism exists.** The only
  protection on staging today is policy.

**How MS-4 avoids emailing real Keva managers from staging (F5 lean):**

1. Detection and sending run ONLY inside the cron, never on a request (e.g.
   not on checklist submit). Crons do not auto-fire on staging.
2. A code guard: the milestone send path returns "dry-run" unless
   `process.env.VERCEL_ENV === "production"`. A hand-fired staging cron then
   logs the would-be recipients and subject, sends nothing, and writes no
   sent-once rows. Local dev (VERCEL_ENV unset) is also dry-run.
3. The org switch (F10) defaults OFF, so even production sends nothing until
   Gary turns it on.
4. "Send a test to me" renders a sample milestone email from real-looking but
   fixed content and sends it to the clicking ADMIN only — reusing the
   `/api/notify/test` recipient rule. This is the one path allowed on
   staging, and it can only ever reach the person who clicked.

**Not measurable from dev.** Dev (`br-broad-wave-a6vpjdw0`) has **zero**
`TenureMilestone` rows, and both orgs with staff there have 5 active members
and **0 with a start date** (start dates arrive from Square syncs that dev

```
dev br-broad-wave-a6vpjdw0  TenureMilestone rows: 0
dev br-broad-wave-a6vpjdw0  org cf888f2d-f234-48c7-8097-fd5b44b5b3dd  active 5, dated 0
dev br-broad-wave-a6vpjdw0  org cmtrkk5ts0000aipdt44blwmd             active 5, dated 0
```

Staging cannot be read from this machine (`vercel env pull` is banned). **Gary,
please run this in the Neon console** (read-only; it approximates store time zones with the database's UTC date,
which moves a count by at most one day's worth):

```sql
WITH m AS (
  SELECT sm.id AS staff_id, sm."organizationId" AS org_id, sm.status,
         tm."isArchived", tm."archivedAt",
         (sm."startDate" + tm."dayCount") AS achieved_on,
         LEAST(CURRENT_DATE, COALESCE(sm."terminatedAt"::date, CURRENT_DATE)) AS as_of
  FROM "StaffMember" sm
  JOIN "TenureMilestone" tm ON tm."organizationId" = sm."organizationId"
  WHERE sm."startDate" IS NOT NULL
)
SELECT current_setting('neon.branch_id', true) AS branch,
       m.org_id, o."milestonesEnabled",
       count(*) FILTER (WHERE m.achieved_on <= m.as_of AND m.status = 'ACTIVE'
                          AND NOT m."isArchived")                       AS achieved_now,
       count(DISTINCT m.staff_id) FILTER (WHERE m.achieved_on <= m.as_of
                          AND m.status = 'ACTIVE' AND NOT m."isArchived") AS people,
       count(*) FILTER (WHERE m.achieved_on > CURRENT_DATE - 7 AND m.achieved_on <= CURRENT_DATE
                          AND m.status = 'ACTIVE' AND NOT m."isArchived") AS last_7_days
FROM m JOIN "Organization" o ON o.id = m.org_id
GROUP BY m.org_id, o."milestonesEnabled";
```

`achieved_now` is the flood a naive first run would send (times the number of
recipients per store). `last_7_days` is what the F3 lean WOULD send on its
first run. **Run it on `preview/staging` only.** MS-1 is not promoted, so
production has no `TenureMilestone` table and the query would error there;
production's flood size is zero until MS-1 ships and an ADMIN defines
milestones.
