### Schema (additive only) — per G1's lean

```prisma
/// MS-3b (F6, F15). An ADMIN-entered "last raise date" for raises Froot did not
/// see (before the daily wage sync existed). PAY DATA under COMP-1. Its own table
/// ON PURPOSE: thirty StaffMember reads return the whole row, and GET /api/staff
/// sends it to every in-scope MANAGER — a column there would leak. ONLY
/// src/lib/raise-history.ts and the last-raise route's lib may name this model

model StaffLastRaise {
  id             String    @id @default(cuid())
  organizationId String
  staffMemberId  String    @unique
  /// Store-local calendar date. NULL = cleared (the row keeps who cleared it).
  lastRaiseDate  DateTime? @db.Date
  setByUserId    String
  setAt          DateTime  @default(now())

  organization Organization @relation(fields: [organizationId], references: [id])
  staffMember  StaffMember  @relation(fields: [staffMemberId], references: [id], onDelete: Cascade)

  @@index([organizationId])
}
```

### The rules, exact

- **Detection (F5):** read every snapshot for the members' Square ids in this
  org, ordered by `capturedAt`, in one query. A raise happens at snapshot `k`
  (k ≥ 1) when `hourlyRate[k] > hourlyRate[k-1]` and both are non-null. The
  baseline (k = 0) is never a raise. A decrease resets nothing.
  15 → 14 → 15 is a raise at the third snapshot. A job change at a higher rate
  is just a higher rate. The latest raise wins. Its date is `capturedAt` as a
  store-local date in the member's display zone (G2). From/to rates come back
  from `detectRaises` for MS-4 and MS-5, and **never enter the eligibility
  result** (F7).
- **Salaried (F5):** latest snapshot `payType === "SALARY"` → no detected
  raise. A manual date still counts (G4).
- **Effective raise date (F6):** the later of the detected date and the
  non-null manual date. Source: `"detected" | "manual"`.
- **Cooldown boundary:** `cooldownUntil = raiseDate + raiseCooldownDays`. The
  member is in cooldown when member-zone today `< cooldownUntil`. The day
  before is in cooldown. `cooldownUntil` itself is eligible.
- **Status (G5):** in cooldown → `"cooldown"`. Otherwise MS-3a's
  red/yellow/green, unchanged. The `cooldown` criterion is always present
  (MS-3a's `raiseCooldownDays` is 1–730, so it can never be switched off). It
  is `"met"` when out of cooldown and a new state, `"cooldown"`, when in it.
  **Its `detail` text never contains a date.** Dates exist only in the
  `lastRaise` / `cooldownUntil` keys, so redaction is deleting keys and
  nothing else.
- **Visibility (F10, G3):** `getRaiseDetailVisibility` returns the set of
  member ids whose raise dates this viewer may see.
  - It is empty unless `canSeeWages(org, actor)`.
  - Otherwise it reads `compConfidential` only (no rates) and applies
    `compVisibleForMember(actor, flag)`. With no wage row, an ADMIN passes and
    a MANAGER fails.
  - **Store scope** is enforced upstream, as it is today. The /staff roster is
    scoped. The profile `notFound()`s an out-of-scope MANAGER before anything
    is computed.
- **`redactForViewer(result, payVisible)`** is pure. When not visible, it
  returns a copy with `lastRaise` and `cooldownUntil` **deleted** (absent, not
  null). The cooldown line then reads "Recent raise — in cooldown". Both pages
  call it per member before anything renders. The header says MS-4 and MS-5
  must too.
- **The ADMIN route** `PUT` / `DELETE /api/staff/[id]/last-raise`, in order:
  1. `requireMilestones("milestones.manage")`: 404 when Milestones is off, 403
     for MANAGER / STORE / STAFF.
  2. Load the member `findFirst({ id, organizationId })`: 404 if it's not in
     this org.
  3. Overlay off: 404 (the raise feature does not exist without it, F12).
  4. `!canSeeWages(org, actor)` or not visible for this member: 403. Nobody
     may write a value they can't read.
  5. Zod: `{ date: "yyyy-mm-dd" }`, a real calendar date, not after the
     member-zone today.
  6. `PUT` returns `{ success: true, lastRaiseDate }`. `DELETE` sets the date
     to null (the row keeps who cleared it and when) and returns
     `{ success: true }`.

  `cooldownUntil` keys carry them, so redaction is key deletion.
