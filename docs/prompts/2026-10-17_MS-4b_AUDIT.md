## B2 FIRST (Gary asked for it first). What production does today with NOTIFY_EMAIL_PROVIDER unset

### What the code does — log only, no error, reported as success

`src/lib/notify.ts`:

- `emailProviderName()` (`:50-52`) turns unset into `"console"`.
- `getEmailSender()` (`:154-157`) returns `consoleEmailSender` for
  `"console"`. It does NOT throw, and it does not need `RESEND_API_KEY` or
  `NOTIFY_FROM_EMAIL` (those are checked only on the `"resend"` branch,
  `:159-170`). Only a value that is neither throws (`:172-175`).
- `consoleEmailSender.send()` (`:55-69`) writes one line to the Vercel
  function log — `[notify:console] to=… subject="…" html=NNNNb` and the
  plain-text body — and returns `{}`. **It resolves successfully.** Nothing
  leaves Vercel.

So it is neither "silently drop" nor "error". It is **log only, and every
caller treats it as a successful send.** That last part is what matters.

### What each existing email type therefore does on production

| Type | Caller | What happens with the console sender |
|---|---|---|
| Behind-pace alert (`pace.alert`) | `src/app/api/cron/pace-alerts/route.ts:30` → `src/lib/pace-alerts.ts:262-280` | For an org with `paceAlertsEnabled = true`: the `PaceAlertLog` lock is written (`:166-176`), the "send" succeeds, the lock **stays**, an AuditLog `email.sent` row is written with `provider: "console"`, and the cron reports the store as `alerted: true`. **That store's one alert for the month is used up with no email delivered.** If `NOTIFY_EMAIL_PROVIDER` is switched to `resend` mid-month, those stores stay quiet until next month. For an org with the switch off (the default), nothing is evaluated at all. |

| Test (`test`) | `src/app/api/notify/test/route.ts:102-114` | Logged, returns `ok: true` with `provider: "console"` in the response. |

## B3. Back-fill size on staging — for the Neon console, `preview/staging` only

**Tenure half — A4's query, unchanged:** see
`docs/prompts/2026-10-17_MS-4_AUDIT.md` § A4. `last_7_days` is what F3 would
send on the first run; `achieved_now` minus that is what would be recorded
"known".

**Checklist half — new.** Approximates the store-local date with the UTC
date of `completedAt` (moves a count by at most a day). Excludes archived
milestones and terminated staff (F9), and counts only tasks on the member's
own org's checklists (MS-4a's rule).

```sql
WITH named AS (
  SELECT sm.id AS staff_id, sm."organizationId" AS org_id, sm.status,
         tl."completedAt",
         row_number() OVER (PARTITION BY sm.id ORDER BY tl."completedAt", tl.id) AS n
  FROM "TaskLog" tl
  JOIN "Checklist" ch ON ch.id = tl."checklistId"
  JOIN "StaffMember" sm ON sm.id = tl."completedByStaffId"
                       AND sm."organizationId" = ch."organizationId"
),
reached AS (
  SELECT n.org_id, n.staff_id, n.status, cm."isArchived",
         n."completedAt"::date AS reached_on
  FROM named n
  JOIN "ChecklistMilestone" cm ON cm."organizationId" = n.org_id
                              AND cm."taskCount" = n.n
)
SELECT current_setting('neon.branch_id', true) AS branch,
       r.org_id,
       o."milestonesEnabled",
       COALESCE(ms."checklistMilestonesEnabled", false) AS checklist_switch,
       count(*) FILTER (WHERE r.status = 'ACTIVE' AND NOT r."isArchived")            AS reached_now,
       count(DISTINCT r.staff_id) FILTER (WHERE r.status = 'ACTIVE' AND NOT r."isArchived") AS people,
       count(*) FILTER (WHERE r.status = 'ACTIVE' AND NOT r."isArchived"
                          AND r.reached_on > CURRENT_DATE - 7)                       AS last_7_days
FROM reached r
JOIN "Organization" o ON o.id = r.org_id
LEFT JOIN "MilestoneSettings" ms ON ms."organizationId" = r.org_id
GROUP BY 1, 2, 3, 4;
```

## B5. Could a send reach the employee or an out-of-scope manager?

No milestone send path exists yet, so nothing today. In the design, three
paths need care, all covered in the plan:

1. **The employee via a linked account.** `StaffMember.userId` (`@unique`,
   nullable) is the only link between a staff record and a login. An employee
   who is also a MANAGER or ADMIN but whose staff record was never linked
   (`userId` null) would pass a `userId`-only exclusion and be emailed about
   themselves. → fork F15.
2. **Corporate members.** `isCorporate` must short-circuit to ADMINs-only
   BEFORE the manager query, not after; a corporate member with store
   assignments from the Square sync (DECISIONS, MS-4 second pass) would
   otherwise pull in every manager of every store.
3. **Recipients cached at detection.** If recipients were resolved when a
   milestone is first seen and reused, a manager moved off the store (or to
   STORE role) between then and the send would still be mailed. The design
   resolves them at send time; the fixture checks it.

The role arm in SQL (`ADMIN` or `MANAGER`) plus `can(…,
"notify.milestone.receive")` keeps STORE and STAFF out by construction, as in
`pace-alerts.ts:116-139`.

## The plan

As the prompt's Phase 2, steps 1-8, with these forks and choices.

### New forks (need Gary)

**F14 — real sends need production AND the Resend provider. Lean: yes.**
F5 says send only when `VERCEL_ENV === "production"`. Today that test is true
on production while the provider is console. If the leg ran there now (once
milestones are promoted and the org switch is on), it would write `sent` rows,
"send" to the log, and — because a sent milestone stays sent — **those
milestones would never be emailed, even after Resend is switched on**. F3's
7-day rule cannot rescue them; they are already "sent". Lean: the leg sends
only when `VERCEL_ENV === "production"` **and** `emailProviderName() ===
"resend"`. Otherwise it is the dry run: log what it would send, write no
rows. On the day Resend is switched on, F3 handles the backlog exactly like
any other switch-on (≤ 7 days sends, older is recorded "known"). Cost: one
more condition; nothing else changes.

**F15 — "never the employee" checks the link AND the email. Lean: both.**
Exclude any recipient whose `User.id` equals `StaffMember.userId`, **and** any
recipient whose email matches `StaffMember.email` (case-insensitive, trimmed).
The second catches an unlinked account. Cost: a manager who shares an email
address with a different staff member would miss that one email — not a
real case.

**F16 — a partial failure. Lean below.** One email per recipient per day
means one milestone can be in several emails. The prompt says the sent-once row
is written before the send and removed if the send fails (the pace-alert
shape), and the schema carries a `failed` state. Lean: write the rows as
`sent` before sending; after sending, a milestone whose every email failed has
its row **deleted** (tomorrow retries, the pace-alert shape); a milestone where
some emails went and some failed is set to **`failed`** and not retried (a
retry would re-mail the people who got it). Every failed email still gets an
`email.failed` row in the send log, so it is visible on
/settings/notifications.

### Implementation choices (for ratification, not forks)

- **The zone** for "today", the reach date and the 7-day rule is the member's
  display zone (`displayTimeZone`), the same one the Milestones tab uses.
- **No eligible recipients** (everyone switched off) → no row, like pace
  alerts. The milestone ages into "known" after 7 days.
- **Leg placement:** its own function `processMilestoneAlerts()` in a new
  `src/lib/milestone-alerts.ts`, called from the pace-alerts route after the
  pace loop, own `milestones` result key, own try/catch so a failure in one leg
  never stops the other. No new cron entry.
- **The org switch** `Organization.milestoneAlertsEnabled` is read in the
  query (like `paceAlertsEnabled`), so a disabled org writes no rows at all.
- **"Send a test to me"** sends a fixed sample milestone through
  `renderEmail()` to the clicking ADMIN's Clerk primary email (the
  `/api/notify/test` rule), logs kind `milestone` with the subject prefixed
  "Test —", and reports the provider so on production today it reads "logged
  only".
- **The email:** subject "Milestone reached — {org}" (one line per milestone
  in the body); rows of employee, store, milestone title, recognition, the
  suggested message verbatim, and a "Open Milestones" link to
  `/staff/{id}?tab=milestones`. No pay, rate or raise field is read by the
  leg at all, and the fixture asserts the rendered HTML has none.
- **Query cost:** `namedTaskDates()` is one query per member. Only members
  of orgs with the switch on AND checklist milestones on are read; batching is
  not worth it at Keva's size and is noted as a comment.
