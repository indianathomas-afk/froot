## §1 Positions rows → StaffMember, and the CONFID. toggle

**Mapping.** The Positions table is the Square roster card in
`src/app/(app)/settings/labor/labor-settings-client.tsx` (header at
`:1718-1734`, rows `:1737-1812`). It fetches `GET /api/square/labor/roster`
(`src/app/api/square/labor/roster/route.ts:58` → `getStoreRoster`).
`getStoreRoster` (`src/lib/labor-roster.ts:446`) reads `SquareTeamMemberWage`
rows for the store, then looks up `StaffMember` by
`(organizationId, squareTeamMemberId)` (`:473-478`; StaffMember has
`@@unique([organizationId, squareTeamMemberId])`). Each row carries
`staffMemberId: match?.id ?? null` and `displayName` (`:496-497`). **"Not in
Froot" is exactly `displayName === null`, which is exactly `staffMemberId ===
null`** (client `:1739-1742`).

**CONFID. is NOT a StaffMember field, and the route is not a PUT.**
`compConfidential` is on `SquareTeamMemberWage` (`prisma/schema.prisma:3385`),
keyed by Square id. The switch (client `:1800-1808`, ADMIN-only column
`:1729-1733`) calls `patchRow` (`:1553-1590`) → `PATCH
/api/square/labor/roster/[squareTeamMemberId]`
(`src/app/api/square/labor/roster/[id]/route.ts:35`). That route:
`requireSquareLabor()` → `canSeeWages` 403 → Zod
`rosterRowPatchSchema` (`src/lib/labor-roster-hours.ts:139`) → per-key ADMIN
check for `ADMIN_ONLY_ROSTER_PATCH_KEYS` (`:65-71`) → org-scoped composite
lookup → update. **It writes no AuditLog row.** Save behaviour on the client:
optimistic flip, reload-and-error on failure.

So "shaped like the CONFID. route" can only mean the *pattern* (org-scoped
lookup, Zod, 403-not-silent-drop, echo the flag back, optimistic client with
reload on failure). The milestone flag lives on a different model and needs its
own route — see Fork F3.

## §2 Every Milestones read path

There is **no shared roster loader** to filter once. There are four independent
`StaffMember` reads and two shared batched engines:

| # | Path | File:line | What it computes | Member source |
|---|------|-----------|------------------|---------------|
| 1 | `/staff` badges gate | `src/app/(app)/staff/page.tsx:172` (`showOnTime`) | On-Time `:180`, Raise `:207` | roster `findMany` `:59` (`include`, so a new scalar arrives free) |
| 2 | `getRaiseEligibility` | `src/lib/raise-eligibility.ts:427` | raise result per member; calls `getOnTimeForStaff` itself `:526` | caller-supplied `RaiseMember[]` (`:409`) |
| 3 | `getOnTimeForStaff` | `src/lib/attendance.ts:243` | on-time per member | caller-supplied `AttendanceMember[]` |
| 4 | `/staff/[id]` tab gate | `src/app/(app)/staff/[id]/page.tsx:641` (`showMilestonesTab`) | everything below runs only inside it: On-Time `:672`, Raise `:686`, manual last-raise control `:717`, tenure `:744`, checklist `:762` | `findFirst` `:49` (`include`) |
| 5 | `/staff/milestones/report` | `src/lib/milestone-report.ts:91` (`buildMilestoneReport`) | report rows, filters, totals, CSV — all from this one list; calls 2, 3, `namedTaskDatesForMembers` `:129`, tenure `:168`, checklist `:175` | own `findMany` `:91` |
| 6 | MS-4b producer | `src/lib/milestone-alerts.ts:135` (`processMilestoneAlerts`, called from `src/app/api/cron/pace-alerts/route.ts:124`) | tenure + checklist reached → enqueue intents | own `findMany` `:135`, `status: "ACTIVE"` |
| 7 | MS-4b dispatch | `src/lib/notifications/kinds/milestone.ts:113-119` (`resolveRecipients`) | re-checks the member at send time (terminated → no recipients, intent expires) | `findFirst` `:113` |

Totals/counts: the report's counts, filters and CSV are all derived from list 5
(`milestone-report-view.ts` is pure over the rows), so filtering list 5 removes
an ineligible member from every total. No dashboard or other surface reads
milestone data (full sweep of every file mentioning milestones; the remaining
hits are setup/settings CRUD that is about milestone *definitions*, not people).

**Can it be filtered once?** Not literally — four member reads, no common
loader. The closest thing to a shared layer, and my recommendation:

- **Engines (2, 3) enforce it themselves.** Add a REQUIRED
  `milestoneEligible: boolean` to `RaiseMember` and `AttendanceMember`; both
  engines skip ineligible members (no entry in the returned map). Required, not
  optional, so `next build` refuses any present or future caller that forgets
  to pass it — the typecheck becomes the coverage proof.
- **The three list reads filter in the query** — report (5) and producer (6)
  add `milestoneEligible: true` to `where`; `/staff` (1) keeps the person on
  the roster (they are still staff) and gets no badges because the engines
  return nothing for them.
- **`/staff/[id]` (4)**: `showMilestonesTab = canSeeHrTabs &&
  milestonesActive(org) && member.milestoneEligible`. Every per-member
  milestone computation on that page already sits inside this gate, so the one
  change hides tab, badges, raise card, manual last-raise control, tenure and
  checklist.
- **Dispatch (7)**: add `milestoneEligible` to the `resolveRecipients`
  re-check beside `status !== "ACTIVE"`, so an intent queued before the flip
  expires unsent.

## §4 Anything that breaks R1–R8 or needs more schema

- **R1–R8 need exactly one column.** `StaffMember.milestoneEligible Boolean
  @default(true)`. AuditLog already exists with a `metadata Json?`
  (`prisma/schema.prisma:876`) and `writeAuditLog` (`src/lib/audit.ts:34`).
- **R6 is free by construction**: the flag is on `StaffMember`, which is one
  row per person; every store roster row for that person resolves to the same
  `staffMemberId`.
- **R7 is free by construction** if the route is keyed by `StaffMember.id`:
  a "Not in Froot" row has no id, so there is nothing to send.
- **R8 holds without code.** The roster sync writes `SquareTeamMemberWage`, not
  `StaffMember` (`labor-roster.ts writeRoster`). The staff sync routes
  (`src/app/api/staff/sync-square/route.ts:86,107`,
  `src/app/api/staff/[id]/resync-square/route.ts:95`) and the import
  (`src/app/api/staff/route.ts`) are typed Prisma writes with explicit `data`
  fields; there is no raw `INSERT`/`UPDATE "StaffMember"` anywhere in `src/`.
  A new row gets the column default (true). Pay type is not read.
- **R2 × manual last-raise.** The ADMIN's manual last-raise control lives in
  the Milestones tab (`[id]/page.tsx:717`), so it disappears for an ineligible
  member. Per R3 the route `PUT /api/staff/[id]/last-raise` still accepts it
  and nothing is deleted. I would not refuse it in the route.
- **R3 × emails on flip-back.** See Fork F5.

## Forks for Gary

**F1 — Who sees the MILESTONES column.** The Positions card renders for
`canSeeWages` (ADMIN and MANAGER). CONFID. hides its column entirely from a
MANAGER (comment at client `:1725-1728`: "a control they can see but not use
reads as a bug"). R5 says "same toggle component and save behaviour as
CONFID." **Recommend: ADMIN only, column absent for a MANAGER** — R4 already
makes it ADMIN-only to flip.

**F2 — The heading.** The `<h1>` reads "Weekly Labor Model", not "Labor".
**Recommend: `<h1>` becomes "Labor Settings"**, the description paragraph under
it unchanged. Alternative: keep "Weekly Labor Model" as the h1 and rename the
sidebar only.

**F3 — Route.** CONFID. is `PATCH` on a Square-id route against a different
model and writes no audit row. **Recommend: new `PUT
/api/staff/[id]/milestone-eligibility`** keyed by `StaffMember.id`, body
`{ milestoneEligible: boolean }` (Zod), gate `requireMilestones("milestones.manage")`
(404 off, 403 non-ADMIN, 401 signed out — R4 exactly), org-scoped
`findFirst`, update, `writeAuditLog` with action
`staff.milestone_eligibility.update`, entityType `StaffMember`, metadata
`{ staffName, before, after }`, echo the flag back. No-op writes (before ===
after) still 200 but write no audit row. The client switch copies CONFID.'s
optimistic-then-reload behaviour; the roster loader adds `milestoneEligible` to
its `StaffMember` select (`labor-roster.ts:477`) and the row type, `null` for a
"Not in Froot" row.

**F4 — Where the flag is enforced.** §2's recommendation: engines with a
required field + three query filters + the tab gate + the dispatch re-check.
Alternative: filter only at the four member reads and leave the engines
unaware (fewer lines, but a future caller is unguarded).

**F5 — Emails when flipped back on.** "As if it had never been off" (R3) means
the next daily producer run sees milestones reached during the off period.
Existing MS-4b rules then apply unchanged: reached within the last 7 days →
queued and emailed; older → recorded as "known", no email. **Recommend:
accept** — it is R3 read literally and needs no code. Alternative: on flip-off,
record every currently-reached milestone as "known" so nothing is ever sent
for the off period (more code, a write in the toggle route).

**F6 — Fixture for R8.** The sync routes call Square live, so the fixture
cannot run them. **Recommend:** a source assertion that no Square sync/import
file names `milestoneEligible`, plus replaying the staff-sync write payloads
(`squareStartDateData`, the email backfill) against an ineligible MS-6 member
and asserting the flag is still false.
