## Part 1 — The decisions Gary needs to make (plain English)

The report is one read-only page listing, for every person the viewer may
see: milestones reached (with dates), the next one coming up (with the date
and days to go), checklist progress if that switch is on, the On-Time badge
and the Raise status. Everything it needs is already computed by MS-1 to
MS-4a; the report adds no table, no setting and no email.

Ten choices. Each has my lean; Gary rules.

**F1. Where the page lives.**
Gary's brief says "Milestone Report on /staff/milestones", but
/staff/milestones is the setup page and MS-1 ruling 1 (ratified) makes it
ADMIN-only. Managers must see the report, so it cannot be that page itself.
*Lean:* a new page at **/staff/milestones/report**. ADMIN sees every store;
MANAGER sees their own stores. Linked from the /staff header (ADMIN and
MANAGER) and from the setup page (ADMIN). The setup page stays ADMIN-only.
*Alternative:* a "Report" view on /staff itself. Rejected as lean: /staff is
already the busiest page in the app, and it would put the amber raise state
(F3) back on /staff, which MS-3c removed.

**F2. Columns.**
*Lean:* name (links to the person's Milestones tab), home store, start date,
days employed, last milestone reached + its date, next milestone + its date +
days to go, checklist tasks done + next threshold (only when the "Checklist
milestones" switch is on), On-Time badge, Raise status.

**F3. Raise colours on the report.**
*Lean:* show every state — green, amber ("Raise in progress"), red and
"cooldown" — because MS-3c sent managers to "the Milestone page" for amber.
Raise DATES (last raise, cooldown ends) appear only for viewers who may see
that person's pay (F10, the existing rule).
**Gary, please confirm this specifically.** Your MS-3c words were *"Leave it
only on the Milestone page. Managers should be directed by us to the
Milestone page. I don't want 'Raise in progress' self-governed."* I read
"the Milestone page" as the Milestones tab on a person's profile. A report
showing amber for a whole store is a different, wider surface. If you meant
the tab only, the report shows green / red / cooldown and leaves amber off,
exactly like /staff.

**F4. Filters.**
*Lean:* store; milestone type (tenure / checklist / on-time / raise); "reached
in the last 30 / 90 days"; "coming up in the next 30 days"; raise status
(e.g. green only). "Type = tenure" means "people with a tenure milestone
reached or coming up"; "type = raise" means "people with a raise badge".
Store filter matches any of the person's stores the viewer can see, so an
"also works here" person shows under each of those stores, as on /staff.

**F5. Terminated staff.**
*Lean:* hidden by default; a "Show terminated" toggle shows their reached
milestones only. This is what the existing code already does for them: their
count stops at the termination date, they have no "next" milestone, and they
get no raise badge.

**F6. Export.**
*Lean:* CSV download for ADMIN only, built in the browser from exactly the
data already on the page (the existing `downloadCsv` helper). No new server
route, so the CSV can never contain more than the page does. No pay amounts
ever; raise dates only where the admin may see that person's pay. MANAGER: no
export in MS-5. **Gary rules.**

**F7. Sorting.**
*Lean:* default "next milestone soonest first"; people with no next milestone
at the bottom; every column header clickable.

**F8. Phone.**
*Lean:* a card per person at phone width, the table on desktop.

**F9. NEW — a manager's own row.** A manager is usually on their own store's
roster, so they will appear in their own report. The MS-3a row still carries
an **unanswered** question from staging: *should a MANAGER see their own Raise
badge?* (Tommy saw "Raise blocked" on his own /staff row.) The report shows
it more prominently than /staff does.
*Lean:* follow whatever /staff does today (the manager sees their own badge)
and answer the MS-3a question once, for both pages. If Gary says "no", both
/staff and the report hide the viewer's own raise status in the same change.

**F10. NEW — the Raise filter for pay-confidential people.** A manager who
cannot see a person's pay still sees that person's raise COLOUR (ruling 2 +
F10 hide dates, not colours). So "raise = cooldown" as a filter tells a
manager that a confidential person had a raise recently, though not when.
That is exactly what the badge already tells them on the profile tab, so it
leaks nothing new.
*Lean:* allow it, and say so here so it is a ruling, not an accident.

## Part 2 — Audit findings (A1–A9)

### A1. Where the report can live

- `src/app/(app)/staff/layout.tsx` wraps EVERY /staff route, including
  /staff/milestones and anything under it. It redirects to /dashboard unless
  `can(actor, "staff.view")`. `staff.view` is MANAGE (ADMIN + MANAGER,
  `src/lib/permissions.ts:236`, `:167`). So STORE and STAFF are already
  redirected from any /staff/* page before it renders, and a manager whose
  staff.view is denied by override is redirected too.
- `src/app/(app)/staff/milestones/page.tsx` adds `requireMilestones(
  "milestones.manage")` (ADMIN_ONLY, `permissions.ts:327`). Off → `notFound()`;
  not admin → /dashboard.
- **Option A — `/staff/milestones/report`** (lean). Gates in order: the staff
  layout (staff.view); `requireMilestones()` with NO capability (Milestones
  off → 404 for everyone, ADMIN included — same as the setup page); then an
  explicit ROLE check `ADMIN || MANAGER`, the same check /staff uses for the
  On-Time and Raise badges (`staff/page.tsx:172`) and the profile uses for the
  tab (`staff/[id]/page.tsx:139`). The role is checked explicitly so a
  capability grant can never widen the report past the badges. MANAGER scope
  = `access.storeIds` from requireMilestones, which is the same
  `dbUser.storeAssignments` list /staff uses (`getUserStoreScope`,
  `src/lib/auth.ts:223`).
- **Option B — a view on /staff.** Same gates, but the page already carries
  pay, compliance, sync and import concerns, and the amber state was removed
  from it by MS-3c.
- **Nav:** the sidebar has no milestone link (`sidebar.tsx`, none found). The
  /staff header already shows a "Milestones" link to admins
  (`canSetUpMilestones`, `staff/page.tsx:141`, `:555`). A "Milestone report"
  link would sit beside it, shown when `milestonesActive(org)` and the viewer
  is ADMIN or MANAGER. The link is not the gate; the page re-checks.

dated in each member's zone. The fixture asserts it returns the same list as
`namedTaskDates` for every member. The existing function and its two callers
are left alone (not this phase's business; noted in triage).

**Expected total:** roughly 30–35 queries per page load, **constant in N**,
read only while checklist is on for the 1 extra. The same order as /staff,
which already runs the on-time, raise and compliance batches.

### A3. Pay privacy on a multi-person page

- Raise DATES live only in the `lastRaise` and `cooldownUntil` keys
  (`raise-eligibility.ts` header, MS-3b). No criterion text carries a date.
- `redactForViewer(result, payVisible)` deletes both keys (absent, not null).
- `payVisible` per member = `getRaiseDetailVisibility(org, actor, members)`
  (`src/lib/raise-history.ts`): empty unless `canSeeWages` (overlay on AND
  labor.costs.view), then COMP-1 `compVisibleForMember` per member — which
  FAILS CLOSED for a manager when there is no wage row.
- /staff does exactly this, per member, before render
  (`staff/page.tsx:207–222`); the profile tab does it for one member
  (`staff/[id]/page.tsx:702–709`).
- **The report will do the same, with one structural addition:** all report
  data is assembled by ONE server-side function (`buildMilestoneReport`) whose
  return value IS the client component's props. Redaction happens inside it.
  So the fixture can `JSON.stringify` that return value — the thing that
  becomes the page payload — and search it for raise dates, rather than
  trusting a renderer.
- The report never calls `detectRaises` or `getManualRaiseDates` directly
  (they return rates / dates before redaction). Only `getRaiseEligibility`.
- **No new server route** in the lean plan (F6 CSV is built in the browser
  from the props). If Gary rules for a server CSV route instead, it calls the
  same builder, so it inherits the same redaction.

### A4. Store scope

/staff (`staff/page.tsx:47–73`): ADMIN → every member in the org. Otherwise
members with **some** assignment in the viewer's `storeIds`
(`storeAssignments: { some: { storeId: { in: storeIds } } }`). A member whose
HOME store is out of scope but who also works at a visible store is listed
under that visible store as "Also works here" (DEBT-13, `:480–487`). A member
with no assignments is reachable by ADMIN only (Unassigned).
**The report uses the identical where-clause**, so the set of people is
identical to /staff for every viewer. The store column shows the home store
(`storeAssignments[0]`, primary-first); the store filter matches any of the
person's in-scope stores.

### A5. Terminated, archived, unlinked, corporate

- **Archived staff do not exist.** `StaffMember.status` is `ACTIVE |
  TERMINATED` only (`schema.prisma`, HR-7). "Archived" applies to milestones,
  not people: an archived milestone stays in history if reached on or before
  its archive date, is never "next" (MS-1). The report inherits that from
  `tenureProgress` / `checklistProgress`.
- **Terminated:** shown on /staff with a red "Terminated" badge (HR-15). Tenure
  count stops at the termination date, no next milestone (MS-1 F4); checklist
  likewise; no raise badge (`getRaiseEligibility` skips them); on-time window
  ends at termination (`lookbackRange`). → F5.
- **Unlinked (no Square team member):** on-time is grey "not linked"; raise
  hours / on-time criteria are "no data", so the best they reach is amber
  (F9 never green on missing data); no detected raise; a manager never sees
  their raise dates (no wage row → masked). Tenure and checklist work
  normally. Dev Keva has 1 such member.
- **Corporate:** own "Corporate" group on /staff, shown to managers as well
  (DEBT-9, Gary 2026-08-02) — but only when the manager's query reaches them,
  i.e. they hold an assignment in the manager's stores. Counted in the org's
  zone (`displayTimeZone`). The report shows "Corporate" in the store column.
- **Unassigned:** ADMIN only, as /staff.

### A6. Upcoming dates

- `tenureProgress` already returns `next.dueOn` (start date + dayCount, a
  store-local date) and `next.daysToGo`. `today` must be
  `localDateStr(now, displayTimeZone(member, org))` — the member's primary
  store's own `Store.timezone`, then the org's (`src/lib/hr.ts:280`). This is
  what the tab does (`staff/[id]/page.tsx:737`). Dev Keva has 2 Denver and 7
  Pacific stores (measured MS-1).
- The report computes `today` PER MEMBER, not once per page — a Denver and a
  Pacific member disagree for an hour every evening. Fixture covers both.
- Checklist "next" has **no date**, only tasks to go (`next.tasksToGo`) —
  a task count cannot be projected to a date. The column shows "N tasks to
  go".
- "Reached in the last N days" compares `achievedOn` with the member-zone
  `today` using `daysBetween` (pure, `milestones.ts`).

### A7. Export patterns

Two exist:
1. **Client-side** `downloadCsv(filename, headers, rows)` in `src/lib/csv.ts`
   (with `escapeCell`) — used by `forecasting-client.tsx` and the templates
   export button. Builds the file from data already in the browser.
2. **Server routes** — `/api/hr/training/export`, `/api/templates/export`,
   `/api/forecasting/export` — gated in the route.

No print page pattern fits (print pages are for single templates /
checklists).
**A CSV would expose** exactly the visible columns: names, home store, start
date, days employed, milestone titles and dates, checklist counts, on-time %
and shift counts, raise colour; and raise dates only where already visible.
It would expose no pay amount, because none is on the page. The risk is the
file leaving Froot: a CSV of every person's raise status and on-time % is a
performance-review document sitting in a Downloads folder. That is why the
lean is ADMIN-only (F6).
