### A2. Staff start date and the Square import
- **The staff model has no hire or start date.** `StaffMember` (`schema.prisma:406-477`)
  carries only `createdAt` (when the Froot row was created), `terminatedAt` and
  `rehiredAt`. The Overview tab already renders `createdAt` labelled **"Member
  Since"** (`staff/[id]/page.tsx`, Overview `<dl>`). That is the date the row was
  imported, not a start date. See the triage below.
- **Square `created_at` is not read anywhere.** The `SquareTeamMember` type
  (`src/lib/square.ts:117-127`) leaves the field out. Square does return it on
  `/v2/team-members/search`.
- **Where the import writes:**
  - First import: the client import dialog calls `POST /api/staff`
    (`src/app/api/staff/route.ts:95`, `prisma.staffMember.create`) with
    `squareTeamMemberId` set.
  - Bulk re-sync: `POST /api/staff/sync-square` (`staff.sync.square`, ADMIN_ONLY,
    not grantable) writes only `email` (fill-when-empty), store assignments, and
    termination.
  - Per-member re-sync: `POST /api/staff/[id]/resync-square` writes `fullName`
    (unless `fullNameLocked`), `squareFullName`, `email` and store assignments.
- **Would a re-sync overwrite a hand-edited value?** Today the question doesn't
  arise because no date is stored. The house pattern for "a human value survives a
  resync" is `fullNameLocked` (set on hand edit, respected by resync-square). The
  planned `startDateManual` is the same shape and name style. Under the plan, both
  sync routes would fill `startDate` from Square `created_at` only when
  `startDateManual` is false.
- **Caveat Gary should know:** Square `created_at` is when the Square profile was
  created, not the hire date. For anyone hired before the business moved onto
  Square, it is wrong, and every tenure milestone computed from it inherits that
  error. This is why a hand edit must win, and it may argue for F6 below.

### A6. Timezone helper
- **`localDateStr(instant, timeZone) → "YYYY-MM-DD"`** at `src/lib/reports.ts:51`. It
  is what CAL-2a/2b use (`src/app/api/calendar/due/route.ts`) to get a store-local
  "today", per store and never per server.
- Day arithmetic: `daysBetween(a, b)` in `src/lib/calendar.ts:183`, a calendar diff
  of two "YYYY-MM-DD" strings with no timezone. It is **private** (not exported).
  MS-1 will add its own one-line equivalent in the milestones lib rather than widen
  the calendar module's API.
- The member's zone comes from `displayTimeZone(member, org)` (`src/lib/hr.ts:280`):
  primary store, then org, then default. It is already computed on /staff/[id] as
  `zone`.
- **The tenure rule:** `startDate` is `@db.Date` (a calendar date, not an instant;
  the CAL-1 S5-D77 precedent, plus `PaceAlertLog.month` and `UsageDaily.date`).
  Today = `localDateStr(now, zone)`. Days employed = `daysBetween(startDate, today)`.
  A milestone is achieved when its `dayCount` ≤ days employed. Nothing is ever read
  in UTC.

### Schema (additive only, house style applied)

```prisma
model Organization {
  …
  // MS-1. Plain per-org column on the calendarEnabled pattern (A1). No env
  // availability var. Ruling 1: toggle on /settings, ADMIN-only.
  milestonesEnabled       Boolean   @default(false)
  tenureMilestones        TenureMilestone[]
}

model StaffMember {
  …
  // MS-1. A calendar DATE, not an instant (@db.Date, the CAL-1 S5-D77 precedent).
  // Tenure is computed from this in the member's store-local today. Null = none
  // entered: an org without Square types it by hand.
  startDate        DateTime? @db.Date
  // MS-1. fullNameLocked's shape: a hand edit sets true, and both Square sync
  // routes then leave startDate alone. False = Square created_at may fill it.
  startDateManual  Boolean   @default(false)
}

model TenureMilestone {
  id              String   @id @default(cuid())
  organizationId  String
  /// Days from startDate, > 0 (checked in the route's Zod schema). No two
  /// NON-ARCHIVED milestones in an org share a dayCount, enforced in the write
  /// routes (see the note below).
  dayCount        Int
  title           String
  recognition     String   @db.Text
  employeeMessage String   @db.Text
  /// House style is isArchived Boolean (Template, CalendarEvent, Training…), not
  /// the prompt's archivedAt. Archived = excluded from every computation.
  isArchived      Boolean  @default(false)
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt

  organization Organization @relation(fields: [organizationId], references: [id])

  @@index([organizationId, isArchived])
}
```

- **Two deviations from the prompt's block, both in house style:** `isArchived Boolean`
  instead of `archivedAt DateTime?` (five models use `isArchived`; none use
  `archivedAt`), and `recognition`/`employeeMessage` as `@db.Text`. If Gary wants the
  archive timestamp, it is `archivedAt DateTime?` instead. That is equally cheap.
  Say which.
- **The duplicate dayCount rule is enforced in code, not by a partial unique index.**
  The repo has exactly one partial unique index
  (`20260720000000_labor0…/migration.sql:73`, `LaborSettings_org_default_key … WHERE
  "storeId" IS NULL`), and it was hand-added to the SQL. Prisma can't express it in
  `schema.prisma`, so every later `migrate diff` would try to drop it. The POST and
  PATCH routes check, inside one transaction, that no other non-archived row in the
  org has the same `dayCount`, and return 409 otherwise. Un-archiving runs the same
  check.
- **No "achieved" table.** Achieved and upcoming are computed (A6 rule), so a
  start-date correction re-flows instantly.
- **F3, if Gary rules yes:**
  ```prisma
  /// MS-1 (F3). Append-only history of a member's CURRENT wage as seen at each
  /// roster sync. Written ONLY when the wage differs from the latest snapshot.
  /// NO READER IN MS-1. MS-3 reads it, and every read must apply
  /// SquareTeamMemberWage.compConfidential (COMP-1) for the same key.

    id                 String   @id @default(cuid())
    organizationId     String
    squareTeamMemberId String
    payType            String?
    hourlyRate         Decimal? @db.Decimal(10, 2)
    annualRate         Decimal? @db.Decimal(12, 2)
    jobId              String?
    wageVersion        Int?
    capturedAt         DateTime @default(now())
    organization Organization @relation(fields: [organizationId], references: [id])
    @@index([organizationId, squareTeamMemberId, capturedAt])
  }
  ```
