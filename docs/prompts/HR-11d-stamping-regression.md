## 1. The defect

Three behaviors worked on **2026-07-24** and do not work now, on the **Keva 2026
Employee Handbook** (`HrDocument.kind = "Acknowledgment"`, Keva org):

1. Signatures never place above or below the signature line.
2. After signing, signatures do not appear on each signature line.
3. `Name:` and `Date:` fields do not populate.

**Evidence held by Gary:**
- A signed record stamped **2026-07-24** has Name / Date / Store filled and a
  signature block rendered on **page 22**.
- A record completed **2026-08-12** has **page 22 blank**.
- Same document. Six weeks apart.

These are Keva production records — the audit runs against **production**
(`ep-green-smoke` / `br-sparkling-block`), **read-only**.

## 2. Leading hypothesis (to confirm or kill, not to assume)

`ensureSignedRecord` in `src/lib/hr-signed-pdf.ts` gates **all** inline stamping
on:

```ts
const anchors = await prisma.documentAnchor.findMany({
  where: { hrDocumentVersionId, confirmed: true },
})
if (anchors.length > 0) { /* every stamp lives inside this block */ }
```

Per HR-11b ruling (a), `DocumentAnchor` binds to `hrDocumentVersionId` —
coordinates are per-file, so anchors do **not** carry forward across versions.
Checkpoints are document-level and do carry forward. Each new version upload
re-detects and must be **re-confirmed by an admin**.

Zero confirmed anchors ⇒ the block no-ops ⇒ certificate-only output, silently.
That single condition would produce all three reported symptoms simultaneously.

Corollary worth testing: `SignatureStamp` checkpoints are **generated by anchor
confirmation**. No confirmed SignatureStamp anchors ⇒ no `Signature` checkpoints
⇒ the 8-12 signer was never prompted to sign at all, and the appended
certificate's checkpoint table will show no `Signature` rows.

**Ranked alternates — each must be explicitly ruled in or out with evidence:**

| # | Hypothesis |
|---|---|
| A | New version uploaded since 7-24; anchors detected as proposals, never confirmed |
| B | Same version; confirmed anchors discarded during a rescan + re-confirm (keep=false) |
| C | New version uploaded; detection ran and matched nothing (different PDF export — signature lines drawn as graphics, not underscore runs; known fill-gate limitation, DECISIONS §HR-11b l) |
| D | `unpdf` detection failed silently at upload — `POST /api/hr/documents/[id]/versions` calls `detectAndStoreVersionAnchors` **best-effort with no error surfacing**, unlike the rescan route which returns 500 |
| E | DOC-1 (audience-gated document grants) introduced a new version or document row as a side effect |
| F | Something else — dependency drift in `unpdf` / `pdf-lib`, a `placement` value change, a `pageRotation` regression |

Do not stop at the first hypothesis that fits. Kill the others on evidence.

### 3c. The decisive queries (production, read-only)

Echo the `DATABASE_URL` **host** first and confirm it is `ep-green-smoke`.
Every query carries the branch literal in the same SELECT.

**Q1 — Which version does each signed record bind to?** This alone separates
hypothesis A/C/E from B.

```sql
SELECT 'br-sparkling-block' AS branch,
       sr.id, sr."completedAt", sr."hrDocumentVersionId",
       v."versionNumber", v."isCurrent", v."fileName", v."createdAt" AS version_created
FROM "HrSignedRecord" sr
JOIN "HrDocumentVersion" v ON v.id = sr."hrDocumentVersionId"
JOIN "HrDocument" d ON d.id = v.<document fk>
WHERE d.title ILIKE '%handbook%'
ORDER BY sr."completedAt";
```

**Q2 — Confirmed anchor count per version of that document.** The direct test of
the leading hypothesis.

```sql
SELECT 'br-sparkling-block' AS branch,
       v.id, v."versionNumber", v."isCurrent", v."createdAt",
       COUNT(a.id) FILTER (WHERE a.confirmed) AS confirmed_anchors,
       COUNT(a.id) FILTER (WHERE NOT a.confirmed) AS unconfirmed_anchors,
       COUNT(a.id) AS total_anchors
FROM "HrDocumentVersion" v
JOIN "HrDocument" d ON d.id = v.<document fk>
LEFT JOIN "DocumentAnchor" a ON a."hrDocumentVersionId" = v.id
WHERE d.title ILIKE '%handbook%'
GROUP BY v.id, v."versionNumber", v."isCurrent", v."createdAt"
ORDER BY v."versionNumber";
```

**Q3 — Anchor detail for the version the 8-12 record is bound to**, and the same
for the 7-24 version. Compare side by side: `markType`, `placement`, `page`,
`x`, `y`, `pageRotation`, `confirmed`, `generatedCheckpointId`,
`anchorText`. Pay attention to page 22 and to any `placement` value that is not
one of the expected `Right` / `Above` / `Below`.

**Q4 — Checkpoints and acknowledgments behind each of the two records.** Count
rows by checkpoint type for both. A missing set of `Signature` checkpoints on the
8-12 record confirms the corollary above.

**Q5 — Version history dates.** When was each version of the handbook created,
and does any creation date land between 2026-07-24 and 2026-08-12? Cross-check
against the DOC-1 promotion date.
